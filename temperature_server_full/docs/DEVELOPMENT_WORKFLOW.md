# 🔧 開発ワークフローとコード変更ガイドライン

## 📋 概要

このドキュメントは、温度サーバーシステムのコード変更を行う際に従うべき開発ワークフローとガイドラインを定義します。プロフェッショナルなアーキテクチャー設計の観点から、品質の高いコード変更を実現するためのルールを記載しています。

---

## 🎯 基本原則

### 1. プロフェッショナルなアーキテクチャー設計

- **設計優先**: コード変更前に、アーキテクチャー全体を理解し、適切な設計判断を行う
- **責務の分離**: 各レイヤー（API、サービス、データベース、UI）の責務を明確に保つ
- **影響範囲の把握**: 変更がシステム全体に与える影響を事前に評価する

### 2. 承認ベースの変更プロセス

**❌ 禁止事項:**
- ユーザーの明示的な承認なしにコードを変更すること
- 推測に基づいて実装を進めること

**✅ 必須事項:**
- 変更内容を明確に説明し、ユーザーに承認を得てから実装を開始する
- 変更計画を提示し、フィードバックを受けてから実行する

---

## 📝 コード変更プロセス

### ステップ1: 要件の理解と確認

1. **指示の解釈**
   - ユーザーの要求を正確に理解する
   - 技術的な背景や制約を確認する

2. **不明点の明確化**
   - 指示があいまいな場合、必ず質問する
   - コード生成に問題が出そうな場合は、事前に確認する
   - 複数の解釈が可能な場合は、選択肢を提示して確認する

### ステップ2: 変更計画の提示

変更を実行する前に、以下を含む変更計画を提示する：

```
【変更計画】
1. 変更の目的: [何を解決/改善するか]
2. 影響範囲: [どのファイル/モジュールが影響を受けるか]
3. アーキテクチャー上の考慮事項: [設計上の判断]
4. 実装アプローチ: [どのように実装するか]
5. リスク評価: [潜在的な問題点]
```

**ユーザーの承認を得てから実装を開始する**

### ステップ3: 実装と検証

1. **実装**
   - 承認された計画に従って実装する
   - コード品質を維持する（可読性、保守性、パフォーマンス）

2. **検証**
   - 変更が意図通りに動作することを確認する
   - 既存機能への影響がないことを確認する

---

## ⚠️ 問題解決の原則

### 失敗時の対応ルール

**❌ 禁止事項:**
- 同じレイヤーでの類似した変更を2回以上繰り返すこと
- 表面的な変更で問題を解決しようとすること
- 同じアプローチを何度も試すこと

**✅ 必須事項:**
- **1回目の失敗後**: 別の角度から調査する
- **2回目の失敗後**: より深いレイヤー（根本原因）を調査する
- **根本原因分析**: 問題の本質を理解するまで、表面的な修正を避ける

### 調査の深さレベル

```
レベル1: 表面的な修正（関数内のロジック変更）
    ↓ 失敗した場合
レベル2: モジュール間のインターフェース変更
    ↓ 失敗した場合
レベル3: アーキテクチャーレベルの設計変更
    ↓ 失敗した場合
レベル4: システム全体の再設計検討
```

**原則**: 同じレベルでの変更は1回まで。失敗したら必ず次のレベルへ進む。

## 📊 変更履歴の記録

### 日報への記載

すべてのコード変更は、日報に以下の情報を記載する：

```markdown
## 変更履歴

### [日付] [変更タイトル]

**変更目的:**
- [変更の目的と背景]

**変更内容:**
- ファイル: `path/to/file.py`
  - 変更箇所: [具体的な行番号や関数名]
  - 変更内容: [何を変更したか]
  
**影響範囲:**
- [影響を受けるモジュールや機能]

**検証結果:**
- [動作確認の結果]
```

### 変更記録の例

```markdown
## 変更履歴

### 2025-01-XX API エンドポイントのエラーハンドリング改善

**変更目的:**
- 不正なリクエストに対するエラーレスポンスを統一する

**変更内容:**
- ファイル: `app/routes/api.py`
  - 変更箇所: `@api_bp.route('/temperature', methods=['POST'])` (行 45-78)
  - 変更内容: バリデーションエラー時のレスポンス形式を統一、エラーメッセージを詳細化
  
- ファイル: `utils/validators.py`
  - 変更箇所: `validate_temperature_data()` (行 12-35)
  - 変更内容: バリデーションロジックを強化、エラーメッセージを改善

**影響範囲:**
- API エンドポイント `/api/temperature`
- クライアント側のエラーハンドリング（必要に応じて更新）

**検証結果:**
- 正常なリクエスト: ✓ 正常に処理される
- 不正なリクエスト: ✓ 適切なエラーメッセージが返される
- 既存機能: ✓ 影響なし
```

## 🔍 調査と分析のガイドライン

### 問題発生時の調査手順

1. **現状の把握**
   - エラーメッセージやログを確認
   - 問題が発生している箇所を特定

2. **影響範囲の分析**
   - どのモジュールが関与しているか
   - データフローを追跡する

3. **根本原因の特定**
   - 表面的な症状ではなく、根本原因を探る
   - アーキテクチャーレベルでの問題がないか確認

4. **解決策の検討**
   - 複数の解決策を検討する
   - 各解決策のメリット・デメリットを評価

5. **実装前の承認**
   - 解決策を提示し、ユーザーの承認を得る

## 📐 アーキテクチャー設計の考慮事項

### レイヤー構造の理解

```
┌─────────────────────────────────┐
│   Presentation Layer            │  ← テンプレート、API レスポンス
│   (templates/, app/routes/)     │
├─────────────────────────────────┤
│   Business Logic Layer           │  ← ビジネスロジック、バリデーション
│   (services/, utils/)           │
├─────────────────────────────────┤
│   Data Access Layer              │  ← データベース操作
│   (database/)                   │
├─────────────────────────────────┤
│   Infrastructure Layer           │  ← システム設定、ネットワーク
│   (config.py, services/)        │
└─────────────────────────────────┘
```

### 変更時の考慮事項

- **レイヤーの責務**: 各レイヤーの責務を超えた変更をしない
- **依存関係**: 上位レイヤーから下位レイヤーへの依存を保つ
- **インターフェース**: モジュール間のインターフェースを変更する場合は、影響範囲を慎重に評価する

---

## 🚫 禁止事項のまとめ

1. **承認なしの変更**: ユーザーの承認なしにコードを変更すること
2. **推測による実装**: 不明確な点を推測して実装すること
3. **同じ変更の繰り返し**: 同じレイヤーでの類似した変更を2回以上繰り返すこと
4. **表面的な修正の継続**: 根本原因を調査せずに表面的な修正を続けること
5. **変更履歴の未記録**: 日報に変更内容を記載しないこと

## ✅ チェックリスト

コード変更を行う前に、以下を確認する：

- [ ] ユーザーの要求を正確に理解したか
- [ ] 不明点があれば質問したか
- [ ] 変更計画を提示し、承認を得たか
- [ ] 影響範囲を評価したか
- [ ] アーキテクチャー上の考慮事項を検討したか
- [ ] 類似した変更を繰り返していないか
- [ ] 根本原因を調査しているか（問題発生時）
- [ ] 変更履歴を日報に記載する準備ができているか
