# デバイス識別設計 (3 層分離アーキテクチャ)

センサーノードを識別・命名・接続する仕組みを、責務ごとに 3 つの独立した層で
管理する設計方針。2026-07-30 に旧「SENSOR_ID に IP を埋め込む」方式から
本方式に切替。

## 3 つのレイヤー

| レイヤー | 目的 | 実装 | 誰が決める |
|---|---|---|---|
| **識別 (identity)** | このチップは物理的にどれか | **MAC アドレス由来の device_id** | 自動 (チップ固有の MAC から生成) |
| **ネットワーク (network)** | どの IP でつながるか | **DHCP 予約** (dnsmasq) | Pi 側管理者 |
| **表示 (label)** | 人間にとって何と呼ぶか | **nickname** (device_nicknames テーブル) | Pi のダッシュボードで管理者 |

## 旧方式との違い

### 旧方式 (2026-07-27 まで)

```
SENSOR_ID = "ESP8266_ip208_30sec"  ← IP + 間隔を埋め込んだ手作りID
fixedIP   = 192.168.4.208           ← ESP 側で WiFi.config 静的宣言
SENSOR_NAME = "DS18B20-ESP8266-208" ← 手動で "-208" を末尾に付ける
```

**問題点**:
- 3 箇所を手動で一致させる必要 (書き忘れリスク)
- チップごとにスケッチを書換え → コピペミス発生源
- IP を変えたら 3 箇所全部書換え
- チップ交換したら全部作り直し
- 「別チップが同じ ID を名乗る」事故が起きても検知手段が薄い

### 新方式 (2026-07-30 以降)

```cpp
// ESP スケッチ側 (全チップ共通、書換えゼロ)
uint8_t mac[6];
WiFi.macAddress(mac);
char deviceId[16];
snprintf(deviceId, sizeof(deviceId), "ESP-%02X%02X%02X",
         mac[3], mac[4], mac[5]);
// 例: "ESP-A1B2C3" (MAC 下位 3 バイトから 6 hex)

WiFi.mode(WIFI_STA);
WiFi.begin(apSSID, apPassword);   // WiFi.config なし、DHCP に委ねる
```

```
# Pi 側 /etc/dnsmasq.d/wlan1.conf に 1 行追加
dhcp-host=aa:bb:cc:a1:b2:c3,192.168.4.208,ESP-A1B2C3
```

```
# ダッシュボード管理画面で nickname 割当
device_id "ESP-A1B2C3" → nickname "冷却塔1"
```

**メリット**:
- **スケッチはコピペで書込み**、per-chip 書換え不要
- **重複しない** (MAC は物理的にユニーク)
- **チップ交換時**: 新チップの MAC を Pi の dnsmasq に 1 行足せば、同じ IP・
  同じ表示名で継続 (スケッチ側は無変更)
- **識別と表示の分離**: 「冷却塔1」の nickname は物理チップとは独立して管理

## MAC を 6 hex 短縮する理由

`WiFi.macAddress()` は `"84:CC:A8:12:34:56"` の 17 文字。全体を device_id に
使うと長すぎる。**下位 3 バイト (6 hex)** で:

- ESP-WROOM-02 の OUI (前半 3 バイト = Espressif 割当) は全チップ共通なので、
  下位 3 バイトだけで区別可能
- 6 hex = 16^6 = 約 1670 万通り、実運用の 10-100 台オーダーでは衝突ほぼゼロ
- "ESP-A1B2C3" の 10 文字は読みやすく、口頭・書面での伝達も楽

MAC 全体が必要なのは:
- ESP-NOW でペアリング相手を指定するとき (masterMAC[6])
- dnsmasq の `dhcp-host=` エントリで予約するとき

これらは Pi 側で管理する情報なので、ESP スケッチ側では下位 3 バイトで十分。

## 動作フロー (新規チップ導入時)

```
1. 新チップに `Get_MAC_Address.ino` を書き込む
   → Serial モニタで MAC 表示: "84:CC:A8:12:34:56"

2. Pi の /etc/dnsmasq.d/wlan1.conf に 1 行追加:
   dhcp-host=84:cc:a8:12:34:56,192.168.4.210,ESP-123456
   $ sudo systemctl restart dnsmasq

3. 本番スケッチ (ESP8266_DeepSleep_FixedIP_Sensor.ino) を新チップに書込む
   ※ スケッチはコピペ、per-chip 書換えなし

4. 起動すると:
   - MAC から自動で device_id = "ESP-123456" を生成
   - DHCP 予約により 192.168.4.210 が割り当てられる
   - Flask に POST → ダッシュボードに "ESP-123456" が表示される

5. ダッシュボードの管理画面で nickname 割当:
   ESP-123456 → "冷却塔3"
```

## 電池省電力への影響

「静的 IP をやめて DHCP 予約にすると電池が減る?」という懸念について:

| 方式 | 起動〜送信時間 | 電池寿命への影響 |
|---|---|---|
| WiFi.config 静的 IP | 約 500 ms | 基準 |
| DHCP 予約 (dnsmasq) | 約 500-600 ms | -1〜2% (誤差レベル) |
| DHCP 無予約 (プールから割当) | 約 800-1500 ms | -3〜5% |

**DHCP 予約と静的 IP の実効的な違いはほぼゼロ**。dnsmasq が事前に MAC-IP
マッピングを持っているので、DHCP 折衝は 1 往復で完了 (通常 3-4 往復) する。

したがって「電池 vs 識別堅牢性」は偽の二者択一。両立できる。

## 移行方針

現時点で稼働中の現場実装はゼロなので、**全チップを新方式で構築** する。
既存のスケッチ (SENSOR_ID に IP 埋込) は使わない。

Flask 側は device_id を単なる文字列として扱うので、旧形式 (`ESP8266_ip208_30sec`)
と新形式 (`ESP-A1B2C3`) が混在しても動作は同じ。移行期の互換性を心配する必要なし。
