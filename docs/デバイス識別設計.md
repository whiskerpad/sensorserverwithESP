# デバイス識別設計 (3 層分離アーキテクチャ)

センサーノードを識別・命名・接続する仕組みを、責務ごとに 3 つの独立した層で
管理する設計方針。

- 2026-07-30: 旧「SENSOR_ID に IP を埋め込む」方式から 3 層分離へ切替
- **2026-09-03: ネットワーク層を「DHCP 予約」から「方式D (ESP 側が MAC から
  IP を算出して静的宣言)」へ変更**

## 3 つのレイヤー

| レイヤー | 目的 | 実装 | 誰が決める |
|---|---|---|---|
| **識別 (identity)** | このチップは物理的にどれか | **MAC アドレス由来の device_id** | 自動 (チップ固有の MAC から生成) |
| **ネットワーク (network)** | どの IP でつながるか | **方式D: MAC 由来の静的 IP を ESP 側で自己宣言** | 自動 (MAC から算出) |
| **表示 (label)** | 人間にとって何と呼ぶか | **nickname** (device_nicknames テーブル) | Pi のダッシュボードで管理者 |

3 層が独立しているので、チップを交換しても nickname は付け替えるだけ、
IP を意識せずに済み、スケッチは全チップ同一のままで運用できます。

## アドレス設計

| 範囲 | 用途 | 割当元 |
|---|---|---|
| `192.168.4.1` | Raspberry Pi 自身 (wlan1、ゲートウェイ兼 Flask サーバー) | 固定 |
| `192.168.4.100` 〜 `192.168.4.227` | **ESP センサーノード** | ESP が MAC から算出して自己宣言 |
| `192.168.4.228` 〜 `192.168.4.254` | 一時接続 (スマホ・PC でのメンテナンス) | dnsmasq の DHCP プール |

ESP 側 (全チップ共通、per-chip 書換えゼロ):

```cpp
uint8_t mac[6];
WiFi.macAddress(mac);

// --- 識別層: MAC 下位 3 バイトから device_id ---
char deviceId[16];
snprintf(deviceId, sizeof(deviceId), "ESP-%02X%02X%02X",
         mac[3], mac[4], mac[5]);
// 例: "ESP-A1B2C3"

// --- ネットワーク層: MAC 末尾バイトから IP (方式D) ---
IPAddress fixedIP(192, 168, 4, 100 + (mac[5] & 0x7F));   // .100 〜 .227
IPAddress gateway(192, 168, 4, 1);
IPAddress subnet(255, 255, 255, 0);

WiFi.mode(WIFI_STA);
WiFi.config(fixedIP, gateway, subnet);   // ★ begin() より前に呼ぶこと
WiFi.begin(apSSID, apPassword);
```

Pi 側 `/etc/dnsmasq.d/wlan1.conf` — **ESP 用の記述は一切不要**:

```
interface=wlan1
domain-needed
bogus-priv
dhcp-range=192.168.4.228,192.168.4.254,255.255.255.0,24h
dhcp-option=option:router,192.168.4.1
dhcp-option=option:dns-server,8.8.8.8,8.8.4.4
```

### `100 + (mac[5] & 0x7F)` という式の意味

- `mac[5]` = MAC アドレスの末尾 1 バイト (0-255)
- `& 0x7F` で下位 7 bit を取り出す → 0-127
- `+ 100` → **100-227**

128 通りしか無いので、**同一 AP 配下で末尾 7 bit が一致するチップが 2 台あると
IP が衝突します**。実運用の 10-100 台オーダーでは確率は低いものの、ゼロでは
ありません。導入時は各チップの起動ログで IP を控え、重複したら以下のどちらかで
回避してください。

1. そのチップだけ別個体に差し替える (MAC が変われば IP も変わる)
2. そのチップだけ手動で IP を上書きする (スケッチ内で固定値を指定)

## なぜ DHCP 予約をやめたか

2026-07-30 の設計では、ネットワーク層を dnsmasq の `dhcp-host=` による
DHCP 予約で管理していました。これを方式D に置き換えた理由は 2 つです。

### 理由 1: DeepSleep 運用では DHCP 折衝の時間がそのまま電池を食う

DeepSleep から起きた ESP は、毎回ゼロから Wi-Fi 接続をやり直します。
DHCP を使う限り、起きるたびに DISCOVER → OFFER → REQUEST → ACK の
4 メッセージ分の往復が発生します。

**重要な誤解の訂正:** 「`dhcp-host=` で予約しておけば折衝が短縮される」は
誤りです。予約が決めるのは「サーバーがどの IP を返すか」だけで、
ハンドシェイクの往復回数は変わりません。

| 方式 | DHCP 折衝 | 1 回の起床にかかる追加時間 |
|---|---|---|
| 方式D (静的宣言) | **無し** | 0 |
| DHCP 予約 | DISCOVER/OFFER/REQUEST/ACK の 4 メッセージ | **+3〜5 秒** (実測) |
| DHCP 無予約 | 同上 | 同上かそれ以上 |

### 実測: 電池寿命が約半分になった

**2026-07-30 時点の判断は「DHCP 折衝の電池差は 5% 前後、誤差レベル」でしたが、
これは実測なしの推測で、外れていました。**

2026-08-21 の実機運用で得られた結果:

| 構成 | 電池寿命 |
|---|---|
| 方式D (WiFi.config で静的宣言) | **1 か月以上** |
| DHCP (折衝あり) | **2 週間強** |

概ね **半減**しています。内訳:

- Wi-Fi アクティブ時の消費: 70〜170 mA
- DHCP 折衝による追加通電: **3〜5 秒 / 1 回の起床**
- 送信周期 2 分 = 720 回/日
- 追加消費: 約 **60 mAh/日** → 月間 約 1800 mAh
- 単三 3 本 (実効 2000〜2500 mAh) に対して総容量の 70〜90% を食う

つまり「電池のほとんどを DHCP 折衝の待ち時間に使っていた」ことになります。
DeepSleep 運用では **「起きている時間 × 起きる回数」がそのまま電池寿命**なので、
1 回あたり数秒の差が月単位でこれだけ効きます。

> **教訓:** 「たぶん誤差レベル」で片付けた見積りが、1 か月後の実測でひっくり返りました。
> 電池運用の詰めは推測ではなく実機で計ること。

### 併せて入れる小改善

```cpp
WiFi.persistent(false);                    // flash 書込み省略 (起動 約30ms 短縮 + flash 摩耗防止)
WiFi.mode(WIFI_STA);
WiFi.setPhyMode(WIFI_PHY_MODE_11N);        // 接続高速化
WiFi.config(fixedIP, gateway, subnet);
WiFi.begin(apSSID, apPassword);
```

`ESP.deepSleep()` の第 2 引数は `WAKE_RF_DEFAULT` のままにします。
`WAKE_NO_RFCAL` は消費電力上は有利ですが、温度変動が大きい環境で
接続が不安定になるため本プロジェクトでは採用しません。

> **常時給電 (USB / AC) の ESP は DHCP のままで構いません。** 電池が関係ないので
> 折衝時間はコストになりません。方式D が必須なのは電池 + DeepSleep 運用の機体です。

### 理由 2: 新チップ追加時に Pi 側を触らなくて済む

DHCP 予約では、チップを 1 台足すたびに以下が必要でした。

1. 新チップに MAC 取得スケッチを書き込む
2. Serial モニタで MAC を読む
3. Pi に SSH して `/etc/dnsmasq.d/wlan1.conf` に 1 行追加
4. `sudo systemctl restart dnsmasq`
5. 本番スケッチを書き込む

方式D では **1 と 5 だけ**、しかも 1 は不要になります (IP は起動時に自分で
決めて Serial に出す)。現場で SSH を開かずに増設できるのは実務上大きい。

### 方式D のデメリット (承知のうえで採用)

| デメリット | 実際の影響 |
|---|---|
| IP を管理者が自由に決められない | ダッシュボードは device_id と nickname で識別するので、IP を人間が覚える場面がほぼ無い |
| 末尾 7 bit 衝突の可能性 | 128 通り。導入時に起動ログで確認すれば検知できる |
| チップ交換で IP も device_id も変わる | nickname をダッシュボードで新 device_id に付け替える。SSH は不要 |
| Pi 側に「登録済み機器一覧」が残らない | Flask の device テーブルが実質的な台帳になる |

## 旧方式との違い (2026-07-27 まで)

```
SENSOR_ID = "ESP8266_ip208_30sec"  ← IP + 間隔を埋め込んだ手作りID
fixedIP   = 192.168.4.208           ← 個体ごとに手で書換え
SENSOR_NAME = "DS18B20-ESP8266-208" ← 手動で "-208" を末尾に付ける
```

**問題点**:

- 3 箇所を手動で一致させる必要 (書き忘れリスク)
- チップごとにスケッチを書換え → コピペミス発生源
- IP を変えたら 3 箇所全部書換え
- チップ交換したら全部作り直し
- 「別チップが同じ ID を名乗る」事故が起きても検知手段が薄い

方式D も「ESP 側で静的 IP を宣言する」点は旧方式と同じですが、
**その値を人間が書かず MAC から自動導出する**点が決定的に違います。
スケッチは全チップ同一のままです。

## MAC を 6 hex 短縮する理由 (識別層)

`WiFi.macAddress()` は `"84:CC:A8:12:34:56"` の 17 文字。全体を device_id に
使うと長すぎる。**下位 3 バイト (6 hex)** で:

- ESP-WROOM-02 の OUI (前半 3 バイト = Espressif 割当) は全チップ共通なので、
  下位 3 バイトだけで区別可能
- 6 hex = 16^6 = 約 1670 万通り、実運用の 10-100 台オーダーでは衝突ほぼゼロ
- `"ESP-A1B2C3"` の 10 文字は読みやすく、口頭・書面での伝達も楽

MAC 全体が必要なのは **ESP-NOW でペアリング相手を指定するとき**
(`masterMAC[6]`) くらいです。方式D では dnsmasq に MAC を登録しないので、
Pi 側で MAC 全体を管理する必要はなくなりました。

## 動作フロー (新規チップ導入時)

```
1. 本番スケッチ (ESP8266_DeepSleep_FixedIP_Sensor.ino) をそのまま書込む
   ※ per-chip の書換えは一切なし

2. 起動すると自動で:
   - MAC から device_id = "ESP-123456" を生成
   - MAC から IP = 192.168.4.(100 + mac[5]&0x7F) を算出して静的宣言
   - Flask に POST → ダッシュボードに "ESP-123456" が出現

3. Serial (デバッグ版) or Flask ログで IP を確認し、
   既存機と重複していないことを見る

4. ダッシュボードの管理画面で nickname 割当:
   ESP-123456 → "冷却塔3"
```

Pi 側の作業はステップ 4 のブラウザ操作だけです。
